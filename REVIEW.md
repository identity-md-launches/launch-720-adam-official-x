## Findings by severity

Critical: **no issues found**. High: **no issues found**. Medium: **one issue, fixed**. No unresolved Critical/High/Medium issue was identified within this scope.

### M-01 — permissionless dust staking can indefinitely postpone principal withdrawal (fixed)

Before this fix, any account holding and approving one atomic unit of ADAM could call `stakeFor(victim, 1)`. The call increased the victim's stake and set the victim's entire principal deadline to `block.timestamp + 24 hours`. Repeating before expiry prevented both `unstake` and `exit` indefinitely while the attacker kept transacting. It also re-locked already mature principal. The attacker required no victim allowance or NFT ownership. This is a sustained withdrawal denial of service, not principal theft; it requires continued transactions.

**Fix:** DistributorV2 now stores the constructor's existing `nftClaim_` argument as public immutable `nftClaim`. `stakeFor` checks `msg.sender == nftClaim` and reverts with `OnlyNFTClaim()` before settlement, lock changes or token movement. No administrator can change that address. Being an excluded address does not grant authority. Holders use `stake()` for themselves; even `stakeFor(msg.sender, ...)` is rejected for other callers.

The authorized NFTClaim checks `ownerOf(id) == msg.sender` for every claimed ID, then calls `stakeFor(msg.sender, amount)`. It exposes neither an arbitrary beneficiary nor an arbitrary call forwarder. NFT operators cannot stake for an owner. Direct stakes and the holder's own `claimAndStake` still reset that holder's full principal lock.

**Regression evidence:** `testRepeatedOneWeiGriefCannotDelayWithdrawal` uses a funded, approved attacker at three sub-day intervals and recovers all victim principal at the original deadline. `testFuzzOnlyImmutableNFTClaimMayStakeFor` checks exact rejection and unchanged principal, rewards, allowance and lock before/after maturity. `testSelfStakeForRejectedButStakeWorks`, NFT operator/transfer tests, real deployment/fork claims, and the stateful invariant exercise both authorized success and failure. Existing delegated accounting/lock fuzz tests now use only the immutable authorized caller.

## Assumptions, deployment parameters and responsibilities

- ADAM is the existing reviewed plain fixed-supply, 18-decimal token: 1,000,000,000 ADAM. Staking assumes no transfer tax, rebase or token callback. This source-only change cannot upgrade immutable deployed contracts; it neither migrates existing stakes nor authorizes any deployment.
- The supplied deployment/network records describe **Sepolia, chain 11155111**. The existing scripts' mainnet presets and historical mainnet fork fixtures are distinct from those live addresses. No new mainnet ADAM address or signing authority is inferred. The network deployer must verify target-chain code, token identity, constructor arguments and actual balances before activation.
- The extension order remains oracle → DistributorV2 → NFTClaim → TreasuryV2. `nftClaim_` is a predicted CREATE address, so a constructor code-length requirement would break this order. Verify `distributor.nftClaim() == address(nftClaim)`, the reverse distributor pointer and permanent exclusion after deployment; never activate with an incorrect or zero claim address. There is no setter to repair bad wiring. No creator transactions may be interleaved, and interrupted broadcasts require nonce/state inspection. Unit tests include both script and manual-signer simulation paths.
- NFTClaim is the reviewed immutable code with trusted configured NFT ownership semantics. Reserve exactly **110,000,000e18 ADAM** (100M IMD / 10M Swarm Pepe); existing mainnet preset counts are 2,000 IDs `[0,1999]` and 1,178 IDs `[1,1178]`. Choose a future claim launch, verify snapshot coverage and fund before it; vesting runs from day 0 through day 9, with the claim deadline at launch + 39 days. Burning unclaimed ADAM after the deadline is permissionless.
- Principal lock is **86,400 seconds**, measured in block timestamps, not a promised wall-clock execution time. Reward eligibility remains immediate. An attacker willing to hold principal for 24 hours can still time entry around rewards; this fix prevents same-transaction principal recycling and unwanted lock extensions, not all economic timing strategies. Smart-contract wallets can change their own controllers, and validators can delay inclusion; neither changes the distributor's withdrawal condition.
- Hook-only liquidity defaults to **890,000,000e18 ADAM**; only a positive smaller/equal configured amount is accepted, with sufficient signer balance. The native ETH/ADAM key remains fee 0, spacing 60, opening tick 177240 and position ticks `[108180,177240]`, amount0Max 0. The LP recipient is always `0x000000000000000000000000000000000000dEaD` in the intended hook-only path. Small rounding dust remains with the funder; unused tokens from a smaller allocation remain under that funder's control.
- Permanent LP custody assumes nobody controls dead or can sign for it and that the configured canonical periphery/core retain their reviewed semantics. The NFT still exists; the position cannot be recovered or moved to a new range. Other pools/positions are outside this guarantee. Legacy zero-treasury simulation helpers retain deployer LP ownership and are not the authorized mainnet entry point; `run()` requires hook-only mode. Operators must review the actual mint recipient.
- The operator supplies/reviews creator/funder, existing token, team wallet, future NFT launch, oracle signer and canonical question hash. Existing limits remain 1 ETH per buy/claim, 300 bps slippage floors, 600-second cooldown, 50-bps keeper bounty and the remaining 90/10 holder/team split. Hook fees and their decay, oracle bounds, retry/reroute rules and reward math are unchanged. Arrange keepers, oracle heartbeat/report funding, team pull payments and frontends pinned to the hooked PoolKey. External IMDSTR whitelist revocation/proxy changes and Treasury execution-price/MEV risks from the original audit remain disclosed assumptions, not repaired by a principal lock.
- Frontends display `unlockTime`, use own `stake` or owner `claimAndStake`, and offer `unstake` separately from combined `exit` if a reward asset fails. Reward claims remain callable during the lock subject to the pre-existing token, liquidity, minOut and deadline rules. See `docs/DEPLOYMENT_CHECKLIST.md` for the operational checklist.
